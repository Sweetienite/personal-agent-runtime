## 1. 本阶段实际做成了什么（事实）

把「提交任务 → 逐项审批 → 确定性路由 → 在私有克隆里运行 Worker → Kernel 自己判断改动、生成补丁、跑检查 → 结算 → 审阅 / 接受」做成了一条完整的闭环。**Worker 全是脚本化的测试替身：没有任何真实模型调用，也没有任何真实适配器。** 你可以直接看一遍：`python -B tests/tools/demo_p2.py`（临时目录，约 5 秒，输出已收进证据文件第 6 节）。

**状态机与台账**（`core/states.py`、`core/store.py`）
- 20 个状态、一张显式转换表；同一张表写进台账，**数据库触发器**按它放行：写错的代码或别的进程都做不出非法跳转（有测试把 20×20 共 400 对状态逐一对照）。`RUNNING → ACCEPTED`、`ACCEPTED → RUNNING`、`CANCELED → RUNNING`、回到 `DRAFT` 都不存在。
- SQLite WAL + `synchronous=FULL`，每次状态变化与它的事件在**同一个事务**里；事件只增不改不删，已结束的 attempt 不可变，任务版本逐次加一，任务身份与合同冻结，已决定的审批不可变；所有写入必须在事务内，否则抛错。
- 每次状态变化都带时间戳、原因、关联 attempt 与版本戳；唯一键 `(project_id, idempotency_key)` 做幂等。

**任务合同与结果信封**（`schemas/*.json`、`core/contract.py`、`execution/results.py`）
- 风险等级：R0 纯文本（Worker 只拿到**空文件夹**）、R1 只读、R2 改文件、**R3 一律拒绝**。路径白名单无通配符，`.git`、`.ai/`、任何 `AGENTS.md` / `CLAUDE.md`、敏感路径永远不能被列入也不能被改。
- 验收检查由 **Kernel 自己运行**（argv 列表、无 shell、可执行文件白名单且逐个有参数规则：`python -c`、`npm install`、`go run`、`make -f` 等一律拒绝）。Worker 自述的「测试通过」只作为一段未验证的文字保留，`summary_verified` 恒为 `false`。
- 合同里出现疑似凭据、控制字符、重复 JSON 键整份拒绝，且不入账。

**隔离执行**（`execution/*`、`core/attempt.py`）
- Worker 只在 `attempts/N/workspace/` 里工作：项目在基线提交处的私有克隆（去掉 origin、关 hooks；已提交的敏感文件**不物化**）。
- **Kernel 从不在 Worker 的副本里运行 git**（Worker 能改写 `.git/config`，下一条 git 命令就会执行它的代码；有测试：投毒的 `fsmonitor` 没有被执行）。改动由「把 `workspace/` 与 Kernel 自留的干净 `ref/` 当普通文件比较」得出，补丁由 Kernel 自己的 git 生成，并**应用回干净基线逐文件比对**，证明补丁与被验证的树完全一致。
- 越界一律让 attempt 失败：路径白名单外、受保护路径、符号链接、嵌套仓库、超大文件、含控制字符的文件名、只读任务的任何改动。`__pycache__` 与被项目 `.gitignore` 忽略的新文件只计数。
- 进程运行器：独立会话与进程组；干净环境（固定 PATH、attempt 内私有 HOME 与 TMPDIR，**不继承你 shell 里的任何变量**）；启动 60 s / 无输出 5 min / 总计 20 min 三个独立超时；先温和停止、宽限期后强杀**自己启动的进程组**；进程退出后清理组内残留；输出读取线程不会被「抓着管道不放」的孤儿卡死；输出先脱敏再落盘，有大小上限；回调抛错或 Ctrl-C 时先杀进程组再向外抛。

**路由、健康与失败策略**（`core/router.py`、`core/health.py`、`core/kernel.py`）
- 链条确定：合同显式 `worker` → 只用它（不会悄悄换别人）；否则角色的 primary 加备用链；否则 `default_worker`。逐项检查：是否启用、是否自动类型、模型 slug 不是占位符、能力够不够、**有没有注册适配器**、有没有健康记录挡着。**不评分，不调用任何 AI。**
- 配置在提交时**固化为快照**；之后改 `profiles.toml` 不影响已排队的任务，`par task retry` 才采用新配置（记 `CONFIG_REFRESHED`）。
- 失败按结构化原因分类：限流（含无原因的 429，**绝不当作额度耗尽**）、额度耗尽与鉴权（整个 Provider）、模型不可用（仅该模型）、权限被拒（含退出码 0 的软拒绝，**绝不自动换更高权限**）、暂时性错误、执行失败、未知（超时、无终态的退出 0）。
- `worker_failure_policy`：`ask` 只挂一个换 Worker 的提议、不自行切换；`pause` 进入 `PAUSED`；`safe_auto` 只对 R0/R1 自动重试暂时性错误一次、自动换 Worker 一次，**R2 永不自动**。

**取消、暂停、重试、审批、恢复**
- 取消在 0.25 s 内被运行中的 Kernel 发现；温和停止，宽限期后强杀；检查进程同样；取消先于结果。
- `retry` 永远是**新 attempt、从基线重来**；采用当前配置；写权限从未批准过的任务会重新要求批准（取消后再 `retry` 绕不过去，`run` 开始前还会再核对一次）。
- 批准逐项进行，不存在「全部批准」；协调者提交并指定 Worker 需要你批准；`accept` 只记录「你接受了结果」，**补丁只保存、不应用**——P2 里没有任何代码会修改项目。
- 崩溃恢复：独立线程心跳；别的 Kernel 见心跳过期即结算。Worker 也没了 → 抓取部分改动、`ORPHANED`、释放锁、`RECOVERY_REQUIRED`；Worker **还活着** → 不启动第二个写入者，只有起始时间与记录一致才允许 `--terminate`；领头进程已死但组里还有残留 → 无法确认身份，**拒绝动手**。

**命令行**：`par task submit | list | status | events | result | diff | run | approve | reject | accept | close | cancel | pause | resume | retry | recover`、`par health [clear]`，全部支持 `--json`。`par task run` 收到 Ctrl-C / SIGTERM 会停掉 Worker 并留下干净记录。Worker 输出显示到终端前会转义控制字符。

**测试替身升级**：假 CLI 新增 `delete / symlink / chmod / ignore_sigterm / stray（留孤儿进程）/ flood / write_env / die`；`ScenarioSequence`、`AdapterRegistry`（默认为空）。

### 过程中被测试抓到、已修复的问题（如实记录）

1. **台账文件被原生 `open/close` 过一次**：POSIX 下关闭任一描述符会丢掉同进程其他连接的文件锁，另一进程关闭时可能把 WAL 删掉（表现为 `disk I/O error`）。是崩溃测试在「SIGKILL 一个正在关闭连接的 Kernel」时真实抓到的。已改为只经 SQLite 访问，并加了回归测试和变异检验（M36）。
2. **取消后再重试可以绕过写权限**（设计复查时发现）：现在 `retry` 会重新要求批准，`run` 开始前再核对一遍。
3. **Worker 文字里的转义序列能操纵终端**：合同拒绝控制字符；显示 Worker 文字时转义。
4. **恢复时不能信任崩溃留下的 `ref/` `verify/`**：现在一律重建。
5. 事件保留的内存只按条数封顶、没按字节封顶：已加 32 MiB 字节预算（错误 / 终态 / 用量事件永远保留）。
6. 取消 / 失败后任务可能卡在没有可决定事项的等待状态（拒绝换 Worker 提议时）：现在会转为 `PAUSED`；`retry` 也可用于 `PAUSED` 与「只剩换 Worker 提议」的等待。
7. **Worker 副本目录曾先以默认权限创建、随后才收紧为 0700**：崩溃遍历测试在 Python 3.13 上约一半的运行里抓到——Kernel 恰在复制途中被 `kill -9` 时，`workspace/` 会以 0755 留下（它在 0700 的 attempt 目录里，别人其实进不去，但不符合「创建时就私有」）。现在 `ref/` `workspace/` `verify/` 一律先以 0700 创建再复制，并加了回归测试与 2 项变异检验（M73、M74）。
8. 一个 Ctrl-C 测试在「从后台任务启动测试套件」时会失败（后台任务继承了被忽略的 SIGINT，`os.kill(SIGINT)` 什么也不会发生）。现在测试自行装上默认处理器；产品代码不受影响（`par task run` 的主要停止路径是 SIGTERM，已测）。另外把几处依赖「绝对耗时」的断言改成随耗时缩放，并在占满全部 10 个核心时重跑验证。

## 5. Provider、记忆、权限、凭据与计费安全

- **Provider**：没有执行过任何 Provider CLI，没有模型调用，没有网络。有测试强制：适配器注册表默认为空；源码不导入任何网络库；整条任务流在拦截了 `socket` 的情况下照常完成；只有预期的几个模块会启动进程。即使配置里写 `enabled = true`，任务也只会停在 `BLOCKED_NO_WORKER`。
- **记忆**：台账只存任务事实，不存项目知识。注意：每个 attempt 目录里的 `prompt.txt` 是给 Worker 的**上下文原文副本**（含 `AGENTS.md`、健康的 `STATE.md`、合同），0600，属于任务证据；是否保留由你决定。
- **权限**：Worker 在私有克隆里；干净环境；越界一律失败；R2 永不自动；权限被拒不自动升权；批准逐项、人的动作；`ACCEPTED` 不等于已应用。
- **凭据**：合同含凭据整份拒绝且不入账；Worker 与检查的环境里没有你的任何变量；日志、事件、结果、终端输出先脱敏；已提交的敏感文件不进入 Worker 的副本；数据目录里除 Worker 副本外没有任何对他人可读的文件（有测试检查）。
- **计费**：没有任何购买、切换计费模式或额外付费的代码路径；配置里 `additional_paid_credits` 仍只能是 `false`。

## 6. 问题、限制与未验证事项

1. **检查会运行补丁里的代码**（测试的本质），P2 没有操作系统级沙箱。缓解见 `SECURITY.md`；因为 P2 不可能对真实项目提交写任务，目前风险只限于测试夹具。**进入 P8 之前必须评估 `sandbox-exec` 之类的加固。**
2. 没有 git 的项目（毕业论文、建模全流程）P2 只接受 R0。给它们做只读分析需要「无 git 的快照比较」，留给 P8 前评估。
3. 克隆用 `--no-hardlinks` 复制对象库：对 Runge 这类大仓库每个 attempt 占一份磁盘。`workspace/` 作为证据保留、不自动清理（「不做破坏性清理」是默认规则），清理命令留到 P8 做成带审批的。
4. 重试从基线重来，**不继承**上一份部分改动；接力包是 P6。
5. Worker 若 `setsid` 脱离进程组，Kernel 追踪不到也不会去杀（读管道的线程不会因此卡死，有测试）。
6. 恢复判断依赖心跳与时钟；机器恰好在睡眠中跨过 15 s 阈值，另一个 Kernel 可能把活着的 attempt 误标为 `RECOVERY_REQUIRED`（不丢数据，也不会启动第二个写入者）。
7. 启动子进程与「记录 pid」之间有一个极小的窗口，恰在此刻崩溃可能留下一个未记录的子进程；恢复时会看到 attempt 没有 pid，提示你检查 `ps`。
8. 全部在 macOS + `/usr/bin/git` 上验证；Linux 与 Windows 未验证。真实厂商 CLI 的行为（输出格式、限流语义、额度域）**完全没有验证**，那是 P3 / P4 的工作。
9. 测试套件较重（约 3 分钟，含真实进程的崩溃与信号测试）。已在满载 CPU 下验证不抖动，但在极慢的机器上计时敏感的 4 个模块仍可能超时。

## 10. 计划偏差登记

1. **「独立 Git worktree」实现为私有 `git clone`**，而不是 `git worktree add`。原因：linked worktree 与源仓库共享对象库和 refs，Worker 在里面能改到源仓库的元数据；完整克隆彻底隔离。代价是磁盘占用（第 6 节第 3 条）。
2. 计划里「接力包」（把上一次的部分改动交给下一个 Worker）按总方案属于 P6，P2 只保证部分改动被**捕获并保留**。
3. 除总方案要求的 `submit / status / result / cancel` 之外，同时做了 `run / approve / reject / accept / close / pause / resume / retry / recover / events / diff / list` 与 `par health`：没有它们闭环无法演示、也无法测试审批与恢复。
4. 新增 `docs/KERNEL.md`；`config/providers.example.toml` 只改了注释。
5. 对真实项目的冒烟测试用的是一次性临时台账，**没有**在真实数据目录里创建台账，也没有在里面留下任何任务。
