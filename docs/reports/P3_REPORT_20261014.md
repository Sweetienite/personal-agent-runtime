**Codex 适配器**（`providers/codex.py`，详见 [CODEX.md](../CODEX.md)）
- **只翻译，不做别的**：构造命令行、说明子进程看到什么、把 JSONL 事件翻译成事件、把一次运行的结局分类。进程、超时、取消升级、工作副本、验收仍由 Kernel 负责。
- **可信的执行体**：绝对路径、必须是 OpenAI 签名（团队 `2DC432GLL2`）的二进制本身；ChatGPT.app 里的 `bin/codex` 是未签名的 `sh` 包装脚本，被拒绝；不查 PATH（PATH 上那个 `codex` 是坏的）。
- **固定的调用方式**：`exec --json --ephemeral -s read-only|workspace-write -m <固定模型> -C <工作副本> … -`；提示词走标准输入；沙箱由任务风险等级决定（R0/R1 只读，R2 才可写工作副本）；从不传 `--ignore-user-config`（保住你的 `memories=false`）、`--dangerously-*`、`danger-full-access`、`--add-dir`、`--ignore-rules` 等；真实 Codex 的参数解析器逐项接受（离线实测，两次真实调用也印证）。
- **环境里没有任何 API key**：子进程环境是 Kernel 的干净环境 + `CODEX_HOME` + 代理/证书变量（你的 shell 里有 `HTTPS_PROXY=127.0.0.1:7890`，所以会带上，否则 Codex 连不上）。每次 attempt 前核对 `codex login status`，只有「Logged in using ChatGPT」放行；API key 登录（按量计费）、未登录、无法识别都**拒绝启动**。
- **你的 Codex 配置里会递给模型的额外能力，每次运行都先关掉再证明**：22 个功能开关（应用/连接器、插件、浏览器与桌面控制、子代理、hooks、`memories` 重申……）、配置里定义的 MCP 服务器（`node_repl`）、`notify` 程序（会在沙箱外运行）。证明方法：关掉之后再列一遍，不许有任何 MCP 服务器仍启用、`memories` 必须读作 false；**每次 attempt 前还会复查一次**。证明不了就不启动（`preflight`，没有任何模型调用）。离线对照：模型可见提示词（空目录里量）15 130 → 13 614 字节，`plugin` 提及 5 → 0。
- **失败按官方消息族分类**：只有厂商自己的「usage limit / spend cap」措辞才算额度用尽（消息里有「try again at …」就解析成该 Provider 的到期时间，只在真实且 35 天内才采用）；**裸 429 永远是限流**；登录、模型不存在、瞬时错误各有对应；**不认识的消息是普通失败，不会被猜成额度问题**；流直接结束（退出码 0 却没有 `turn.completed`）是 `UNKNOWN` 而不是成功。被 Codex 拒绝的命令（`declined`）是结果里的警告，不再触发无意义的「权限重试」。
- **取消**：Codex 只会优雅处理 Ctrl-C，所以发 SIGINT；不听的由 Kernel 的既有升级流程收拾（测试覆盖两种进程）。
- **Worker 副本不含 `.git`**（上面第 2 点的修复）：适配器声明 `workspace_with_git = False`；这对 Kernel 没有影响，因为它从不使用 Worker 的仓库，而是把 `workspace/` 与自己留的 `ref/` 当普通文件比较。代价：模型在副本里不能用 `git status` / `git diff`。

### 过程中被实测 / 测试抓到、已修复或已记录的问题（如实记录）

1. **（真实烟测）Codex 往你的全局配置追加信任条目**：见第 0 节第 2 点。定位过程：真实 R2 之后 `config.toml` 多了 3 行；`config.toml` 的修改时间比进程启动晚 0.18 秒（早于任何模型交互）；用一份没有登录的 `CODEX_HOME` 拷贝（只能得到 401，不可能调用模型）做了十余组对照，确定触发条件是「git 工作副本 + `workspace-write`」，且 `-c projects.….trust_level` 挡不住；去掉 `.git` 后不再触发。
2. **（实测）你的 Codex 配置里有一个 `notify` 程序**（桌面控制的辅助程序），Codex 会在每个 turn 结束时在沙箱**外**启动它：现在每次运行都 `-c notify=[]`。
3. **（实测）关掉 `multi_agent` 之后，模型可见的提示词里仍有一段「你可以 `spawn_agent`」的说明**——来自模型目录的基础指令，不随开关变化。工具本身是否可用只有真实运行才能看到；两次真实运行里没有出现子代理调用。已记为「未观察到」而不是「已证明不可用」。
4. **（实测）`--disable <未知功能名>` 会报错**（`Unknown feature flag`），所以功能名单是按已安装版本动态筛的。
5. **（实测）Codex 沙箱不限制读**：见第 0 节第 3 点。
6. **（实测）模型目录里 `tool_mode = "code_mode_only"`**：这个版本的模型通过一个 JS「代码模式」宿主调用工具；两次真实运行里模型只用了 shell 与 `apply_patch`。隔离配方对代码模式下工具命名空间的影响没有被独立验证。
7. **（测试）假 codex 程序的启动脚本因仓库路径里有空格而无法用 `#!` 行**：改成 `sh` 包装。
8. **（测试）`probe()` 在登录目录不存在时先跑了 CLI 才报错**：现在先检查目录存在，再运行任何东西（一个指向不存在目录的 CLI 可能会去创建它）。
9. **（评审）隔离证明缓存 5 分钟，期间你新加的 MCP 服务器会漏过去**：现在每次 attempt 前再用一次 `mcp list` 复查，有新增就重新发现（有测试与变异检验 M97）。
10. **（变异检验）M83 最初「存活」**：它是个等价变异（API key 登录仍会被后面一道检查拒绝，只是提示语不同）；已把测试收紧到要求提示语里点名「按量计费」，并加了「整个登录检查都没了」的变异 M96。
11. **（干净检出的全量测试）一个 P2 的恢复测试偶发失败**：`test_a_cancel_that_was_already_requested_finishes_as_canceled` 在对已提交树做的干净检出里失败了 1 次（此前 12 次全量运行都通过）。原因是测试自身的竞态：它先请求取消、再 `kill -9` 那个 Kernel，若两步之间被调度延迟 50 毫秒以上，还活着的 Kernel 会抢先停掉 Worker，随后测试对已经不存在的进程组发 `killpg` 报 `ProcessLookupError`。我用「在取消与崩溃之间人为加 0.4 秒」确定性地复现了同一个错误，再让这个「注定被杀」的 Kernel 只很少轮询取消（`cancel_check=30`），使顺序确定；产品代码没有变化。这个修正与 P3 的代码无关，但属于我交付的测试套件，所以如实记录。
